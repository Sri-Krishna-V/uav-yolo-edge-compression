# Findings: YOLO26 reality check

Ticket: `issues/01-yolo26-reality-check.md`
Researched: 2026-09-12. Source snapshot: `ultralytics` main branch @ 2026-09-12, PyPI latest `8.4.149`.

**Verdict in one line:** YOLO26 is fully released and usable, and it does **not** break the compression
pipeline — because on every INT8 edge path in this study Ultralytics silently *turns the NMS-free head
off* and falls back to a YOLO11-shaped one-to-many head. The NMS-free property is not obtainable on
Pi 5 / Android / Jetson-INT8 at all. That is the finding the plan has to absorb.

## 3. Architecture — YOLO11 skeleton, two config flags, duplicated head

This is the single most useful thing I found, and it is cheap to verify: **YOLO26 and YOLO11 use the
same `Detect` class and near-identical backbone/neck.** Exact diff of
`cfg/models/11/yolo11.yaml` vs `cfg/models/26/yolo26.yaml` (fetched from main):

```diff
 # Parameters
 nc: 80
+end2end: True   # whether to use end-to-end mode
+reg_max: 1      # DFL bins
...
-  - [-1, 1, SPPF, [1024, 5]] # 9
+  - [-1, 1, SPPF, [1024, 5, 3, True]] # 9
...
-  - [-1, 2, C3k2, [512, False]] # 13      (and 16, 19: False -> True)
+  - [-1, 2, C3k2, [512, True]] # 13
-  - [-1, 2, C3k2, [1024, True]] # 22
+  - [-1, 1, C3k2, [1024, True, 0.5, True]] # 22
   - [[16, 19, 22], 1, Detect, [nc]]   # ← identical head module
```

That is the *whole* topological difference: C3k2/SPPF/C2PSA blocks throughout, same P3/P4/P5 outputs,
same `Detect` module. ProgLoss, STAL and MuSGD are **training-time** changes (loss weighting, label
assignment, optimizer), not graph changes — they leave no trace in the deployed model.

### Size: YOLO26s is *bigger* than YOLO11s

From the YAML scale comments (authoritative, generated by the repo):

| | layers | params | GFLOPs |
|---|---|---|---|
| YOLO11s | 181 | 9,458,752 | 21.7 |
| **YOLO26s** | **260** | **10,009,784** | **22.8** |
| YOLO11m | 231 | 20,114,688 | 68.5 |
| YOLO26m | 280 | 21,896,248 | 75.4 |

YOLO26s is **+5.8% params, +5.1% GFLOPs, +44% layers** over YOLO11s. The layer inflation is largely the
duplicated detection head. Any "YOLO26 is lighter" framing in the deck is wrong and a reviewer will
catch it.

### "DFL removed" = `reg_max: 1`

`ultralytics/nn/modules/head.py`:

```python
self.reg_max = reg_max  # DFL channels
self.no = nc + self.reg_max * 4
...
self.dfl = DFL(self.reg_max) if self.reg_max > 1 else nn.Identity()
```

With `reg_max=1` the DFL module becomes `nn.Identity()` and the box branch emits 4 raw distances
instead of 4×16 bin logits. There is no separate "YOLO26 head" class; it is `Detect` parameterised.

### The head is a **dual head**, and both branches live in the checkpoint

```python
if end2end:
    self.one2one_cv2 = copy.deepcopy(self.cv2)
    self.one2one_cv3 = copy.deepcopy(self.cv3)
```

- `cv2`/`cv3` = one-to-many branch (classic, needs NMS).
- `one2one_cv2`/`one2one_cv3` = one-to-one branch (NMS-free).
- Both are fed from the **same three neck tensors**. In training the one-to-one branch receives
  *detached* features (`x_detach = [xi.detach() for xi in x] if self.training else x`) — comment in
  source: *"detach keeps one2one out of the backbone"*. So the NMS-free branch does **not** shape the
  backbone gradients at all.
- Selection is a settable property: `self.end2end`. Docs confirm the user-facing arg is `nms`
  (`nms=None` → one-to-many + external NMS, the **default**; `nms=False` → NMS-free; `nms=True` → NMS
  baked into the export graph).
- `fuse()` **destroys** the unused branch:
  ```python
  def fuse(self) -> None:
      """Remove the unused detection branch for inference."""
      end2end = self.end2end
      for name in tuple(self._modules):
          if name.startswith("one2one_"):
              setattr(self, name[8:] if end2end else name, None)
  ```
  Docs: *"fusion cannot reconstruct a branch that has already been removed."* **Keep the unfused
  training checkpoint.**

### NMS-free post-processing is a top-k, not magic

```python
scores, conf, idx = self.get_topk_index(scores, self.max_det)   # max_det = 300
...
groups = 8 if self.export and self.format == "engine" and not self.dynamic else 1
```
Output shape `(N, 300, 6)` = `[x1,y1,x2,y2, max_class_prob, class_index]`. The `_grouped_topk` helper
exists specifically to work around TensorRT's top-k limits. `max_det` is **baked into the graph** —
changing it requires re-export.

## 4. Export coverage

Default ONNX opset comes from `best_onnx_opset()` in `ultralytics/utils/export/engine.py`:
`torch>=2.4 → opset 18` (capped at the installed `onnx` library's max). The source comment is worth
quoting because it bites the PTQ plan:

> *"torch>=2.4 supports opset>=19, but ONNX Runtime CUDA has no Resize-19 or ReduceMax-20 kernel, so
> opset>=19 runs those nodes on the CPU and copies their tensors back and forth. **Its static INT8
> quantization also rejects opset>=21.**"*

Per-format precision support (docs `modes/export.md`, Quantization Precision Support table):

| Format | FP32 | FP16 | INT8 | W8A16 | Note |
|---|---|---|---|---|---|
| ONNX | ✅ | ✅ | ✅ | ❌ | INT8 = ONNX Runtime static quant + calibration data |
| TensorRT (`engine`) | ✅ | ✅ | ✅ | ❌ | INT8 needs representative calibration data |
| LiteRT (TFLite) | ✅ | **❌** | ✅ | ✅ | also `"w8a32"` dynamic INT8, no calibration |
| **NCNN** | ✅ | ✅ | **❌** | ❌ | **no INT8 path at all in Ultralytics export** |
| CoreML | ✅ | ✅ | ✅ | ✅ | INT8 is weight-only quantization |

Two of these are plan-relevant surprises:
- **NCNN has no INT8 export in Ultralytics.** If the study wanted NCNN INT8 on the Pi 5 or the M35, that
  requires leaving the Ultralytics export path and driving `ncnn2int8` by hand. Budget for it or drop it.
- **LiteRT has no FP16 export.** The Android FP16 cell must go through ONNX/NNAPI or be dropped.
- The arg is now `quantize=` (`8`, `16`, `32`, `"w8a8"`, `"w8a16"`, `"w8a32"`); `default.yaml` says it
  *"replaces deprecated half/int8 args"*. Old `int8=True` / `half=True` snippets are stale.

### Known export failures (YOLO26-specific)

- **#23282 — YOLO26 TFLite export does not work on Android.** LiteRT 2.1.0 GPU delegate fails to compile
  the exported graph: `GATHER_ND` unsupported, `CAST` with INT64 tensors, `ADD` v>2, `MUL` v5 vs
  supported v4. Reporter notes YOLO11 exports fine. **Closed as "not planned."** Those ops are the
  end-to-end top-k/gather post-processing — i.e. this is the NMS-free head failing on the M35's class of
  device. <https://github.com/ultralytics/ultralytics/issues/23282>
- #23557 — YOLO26 **segmentation** → TFLite INT8 conversion failure (out of scope, detection only).
- #23340 — YOLO26 RKNN INT8 export (out of scope, no Rockchip board).
- #24607 — TensorRT < 8.5.0 lacks the `Mod` operator used by the end-to-end graph.
- #23841 — TensorRT 10.3.0 on JetPack 6 cannot build INT8 NMS-free engines.

## 5. Compression compatibility — **the load-bearing answer**

### 5a. PTQ INT8 calibration — the NMS-free head *does* break it, and Ultralytics auto-disables it

This is settled in code, not inference. `ultralytics/engine/exporter.py`, verbatim:

```python
if hasattr(model, "end2end"):
    model.end2end = self.args.nms is False
if getattr(model, "end2end", False):
    if fmt in {"rknn", "ncnn", "executorch", "paddle", "imx", "edgetpu", "qnn"}:
        # Disable the end2end branch for formats without top-k support
        model.end2end = False
        LOGGER.warning("This export format does not support end2end models, disabling the end2end branch.")
    if fmt == "litert" and self.args.quantize in {8, "w8a16"}:
        # Static activation quantization collapses the end2end class-index output; export raw and run NMS later
        model.end2end = False
        LOGGER.warning("LiteRT INT8 export does not support end2end models, disabling end2end branch.")
    if fmt == "engine":
        if check_version(trt.__version__, "<8.5.0"):
            model.end2end = False   # Mod operator unsupported
        if (self.args.quantize == 8
            and check_version(trt.__version__, ">=10.3.0,<10.4.0")
            and is_jetson(jetpack=6)):
            model.end2end = False
            LOGGER.warning("TensorRT 10.3.0 on JetPack 6 with INT8 cannot build NMS-free exports; "
                           "selecting one-to-many outputs.")
```

**Root cause**, stated by Ultralytics in two places:
- exporter comment: *"Static activation quantization collapses the end2end class-index output."*
- `modes/export.md` FAQ: *"when `nms=False` is enabled, post-processing (including class indices) is
  embedded directly in the exported graph. The `output0` tensor contains class indices … FP16 cannot
  reliably represent integer values above 2048 … `output0` is intentionally kept in FP32."*

The NMS-free head emits a **class index as a numeric channel**. A per-tensor affine quantizer computes
one scale over a range spanning coordinates, a probability in [0,1], and an integer class id in
[0, nc). Quantizing that tensor destroys the index. There is no calibration set that fixes this; it is
a representation problem, not a data problem.

**Mapped onto this study's four platforms:**

| Platform | Intended path | NMS-free available? |
|---|---|---|
| Raspberry Pi 5 | NCNN | **No** — hard-disabled for `ncnn` at any precision |
| Raspberry Pi 5 | LiteRT INT8 | **No** — disabled for `quantize in {8, "w8a16"}` |
| Samsung M35 | NCNN or LiteRT INT8 | **No**, both (and see #23282 for FP16 too) |
| Jetson Nano (JP4, TRT 8.2) | TensorRT | **No** — TRT < 8.5.0 |
| Jetson Orin Nano (JP6, TRT 10.3) INT8 | TensorRT | **No** — unless TRT upgraded to ≥10.7 |
| Laptop CPU | ONNX / OpenVINO FP32/FP16 | **Yes** |

So: **YOLO26's headline feature is unavailable on every INT8 edge configuration in this matrix.** The
Jetson case has a documented workaround — upgrade TensorRT to 10.7.0+ via the CUDA apt repo, per
<https://docs.ultralytics.com/guides/nvidia-jetson/> FAQ *"Why does my TensorRT INT8 export disable
NMS-free inference on JetPack 6?"*. The NCNN and LiteRT cases have **no** workaround.

**The good news, and it is genuinely good:** the fallback is automatic, silent-but-warned, and lands on
the *one-to-many* branch — which is a plain `Detect` head with `cv2`→4 channels and `cv3`→nc channels.
That is structurally simpler than YOLO11's head (which has `4*reg_max=64` box channels plus a DFL
softmax+conv). So:

> **Standard PTQ INT8 calibration is not broken by YOLO26. It is *easier* than on YOLO11**, because
> removing DFL removes a 16-bin softmax and a fixed 1×1 conv from the box decode path — historically a
> sensitive spot for INT8 on YOLOv8/YOLO11. No published quantitative evidence for this claim was found;
> it is a structural argument, and measuring it is a legitimate contribution of your paper.

Also relevant: **QAT is now first-party.** `quantize=8` passed to `train` (docs `modes/export.md`,
shipped ~v8.4.143) runs NVIDIA TensorRT Model Optimizer fake-quant fine-tuning. Documented constraints:
`compile=False` required; *"the output head is deliberately kept in float to limit INT8 accuracy loss"*;
and *"`onnx` and `engine` exports emit them as Q/DQ nodes; **other formats read calibration instead and
reject a QAT checkpoint**"* — so QAT is useless for the NCNN and LiteRT legs. Published COCO deltas:
QAT costs 0.008–0.017 mAP vs FP32, PTQ costs 0.010–0.057, QAT recovers 0.030–0.044 on larger models.

### 5b. Structured channel pruning — **no precedent found; mechanically plausible; this is the real risk**

What I searched: `ultralytics` GitHub issues/PRs for pruning, `VainF/Torch-Pruning` issues/discussions/
examples for YOLO26 and `end2end`/`one2one`, arXiv and Google for "YOLO26 pruning" / "YOLO26 structured
pruning". **Result: zero published YOLO26 pruning work, and no Torch-Pruning example beyond YOLOv8.**

- Ultralytics has **no official pruning**. PR #21977 ("Add optional structured pruning for YOLOv8
  detection models") was **closed unmerged** on 2026-02-14 after stale-bot closure; the contributor
  stated *"Currently supported: YOLOv8 detection models only."*
  <https://github.com/ultralytics/ultralytics/pull/21977>
- Torch-Pruning's only YOLO example is `examples/yolov8/yolov8_pruning.py`, adapted from issue #147.
  No YOLO11 or YOLO26 example.

**Structural assessment (mine, unverified by any source — treat as a hypothesis to test in week 1):**

1. Backbone and neck are the *same module types* as YOLO11 (C3k2 / SPPF / C2PSA / Conv / Concat /
   Upsample). Whatever DepGraph does on YOLO11 it will do here. The two SPPF/C3k2 arg changes alter
   kernel counts and shortcut flags, not the dependency structure.
2. The novel part is the head fork: each of the three neck tensors now feeds **four** consumers
   (`cv2[i]`, `cv3[i]`, `one2one_cv2[i]`, `one2one_cv3[i]`) instead of two. DepGraph handles fan-out
   forks in general, but a channel cut in a neck output **must** propagate consistently into all four,
   and this is untested for this head.
3. `reg_max=1` *removes* a pruning constraint: YOLO11's box branch output must stay a multiple of
   `reg_max=16` for DFL to decode; YOLO26's is a flat 4 channels. One fewer grouping rule.
4. The `x.detach()` on the one-to-one path is `self.training`-gated, so a trace in eval mode (which is
   how DepGraph builds the graph) sees an unbroken graph. Not a problem.

**Recommended de-risking move, and it costs almost nothing:** since you lose NMS-free at INT8 anyway
(5a), set `nms=None` / `end2end=False` and call `fuse()` **before** pruning. That deletes
`one2one_cv2`/`one2one_cv3` outright and leaves a graph that is, for pruning purposes, a YOLO11s with
`reg_max=1` — collapsing the fork problem entirely and letting you reuse YOLO11 pruning tooling
unchanged for both models. Caveat from the docs: *"fusion cannot reconstruct a branch that has already
been removed"* — do this on a copy and archive the unfused `.pt`.

### 5c. Output-level knowledge distillation — sidestepped entirely by first-party KD

**Ultralytics shipped official knowledge distillation in v8.4.77 (2026-06-25, PR #24894.)**
<https://github.com/ultralytics/ultralytics/releases/tag/v8.4.77> ·
<https://docs.ultralytics.com/guides/knowledge-distillation/>

Critically, **it is feature-based, not output-based**:

> *"Features are extracted from both models at the three neck layers that feed the Detect-family head."*
> A projector of two 1×1 convolutions with ReLU aligns each student feature map to the teacher's
> channels. A score-weighted L2 loss compares projected student features with teacher features,
> weighted by the teacher's classification confidence.

Because it taps the **neck**, it never touches the detection head. **The NMS-free head is therefore
irrelevant to the official distillation path** — it works identically on YOLO11 and YOLO26.

Constraints that matter to the plan:
- *"The teacher and student must belong to the same YOLO family … Cross-family distillation (e.g.
  YOLO11 teacher with YOLO26 student) is not supported."* → YOLO11m→YOLO11s and YOLO26m→YOLO26s. This
  is exactly what the map already specifies. No change needed.
- Works for detect/segment/pose/obb, but *"Only detect has been experimentally verified."*
- API: `model.train(data=..., distill_model="yolo26m.pt", dis=6.0)`. `dis` defaults to 6.0.
- Exported student contains **only student weights** — no inference-time cost.
- Published COCO gains: 26n 40.9→41.5, **26s 48.6→49.2 (+0.6)**, 26m 53.1→53.9, 26l 55.0→56.0,
  26x 57.5→57.9. **Budget a ~+0.5 to +1.0 mAP effect, not more.** If your VisDrone run-to-run variance
  is larger than that, the KD arm of the matrix will be unreadable — size the repeat count accordingly.

**On output-level KD specifically** (what the ticket asked about):
- The one-to-many branch still emits classic pre-NMS logits — `(B, 4, A)` boxes and `(B, nc, A)` class
  scores — so conventional logit/box distillation (Hinton-style soft targets on `cv3`, L1/IoU on `cv2`)
  remains expressible on YOLO26 without modification.
- **But `reg_max=1` kills an entire family of methods.** Localization Distillation (LD) and every
  DFL-distribution-matching variant distil the teacher's 16-bin box distribution. YOLO26 has no such
  distribution — the box output is a point estimate. **LD and DFL-based KD are inapplicable to YOLO26 by
  construction.** This is a clean, citable asymmetry between your two study models and worth a sentence
  in the paper.
- The end-to-end branch output `(B, 300, 6)` is post-top-k and post-argmax. It is **not** usable as a
  distillation target — no dense logits, and a non-differentiable index channel.

**Bottom line on 5:** nothing in the compression pipeline is blocked. Use first-party KD (feature-based,
head-agnostic), PTQ on the auto-selected one-to-many head, and prune after fusing away the one-to-one
branch. The thing you lose is not capability — it is the *NMS-free story*.

Reading it honestly:
- **YOLO26s beats YOLOv8s by +1.0 mAP50 / +0.3 mAP50-95.** Small.
- **YOLO26n *loses* to YOLOv8n** (−0.6 / −0.7). The STAL small-object claim does not hold at n-scale here.
- The paper's own conclusion: *"NMS-free design does not inherently guarantee superiority in universal

  occupy fewer than 2,000 pixels."*

Caveats: third-party arXiv preprint, no stated peer review; no YOLO11 baseline (so it does not directly
answer *your* comparison); YOLO26 evaluated NMS-free while YOLOv8 used NMS, which is not a clean
control — and since the one-to-many head is 0.6–0.8 mAP *better*, YOLO26's numbers here are likely
slightly understated.

**Other UAV work, weaker evidence:**
- *MD-YOLO: An Improved YOLO26-Based Model for Small-Object Detection in UAV Aerial Imagery*,

  **I could not retrieve the numbers — mdpi.com returns HTTP 403 to the fetch tool.** Worth a manual
  read; it is the closest published analogue to your baseline. ⚠️ Its abstract claims YOLO26
  *"benefits from … Distribution Focal Loss"*, which is **factually wrong** (`reg_max: 1` removes DFL).
  Treat its architectural descriptions with suspicion.
- HuggingFace `dronefreak/visdrone-yolov26n` and `dronefreak/visdrone-yolov26l` exist — community
  uploads, no paper, no verified protocol. Not citable.

**Unknown:** no published YOLO26 **YOLO11-controlled** VisDrone comparison, and no published YOLO26
VisDrone result under INT8/pruning/distillation, on any edge device. Searched arXiv, Google Scholar
surface results, MDPI, and Ultralytics docs/issues. **That gap is your paper.**

## Implications for the plan

1. **Reframe the YOLO26 angle.** "NMS-free inference at the edge" is not a deliverable — it is
   unobtainable on Pi 5 (NCNN), Android (NCNN/LiteRT-INT8), and Jetson INT8. The honest and more
   interesting framing: *"the architectural change that YOLO26 advertises is exactly the one that
   quantization tooling rejects; what actually reaches the edge is a DFL-free one-to-many head, and
   here is what that is worth."* That is a stronger, more publishable observation than another mAP table.
2. **Add a matrix cell, cheaply:** one-to-many vs one-to-one on the *laptop/ONNX FP32* leg only, where
   both are available. It costs one extra export + val and gives you the 0.6–0.8 mAP / latency trade-off
   *measured on VisDrone* rather than borrowed from COCO. That is a clean, citable mini-result.
3. **Fix a wrong assumption: NCNN INT8 is not available through Ultralytics export.** Decide now:
   drop NCNN INT8, or budget manual `ncnn2int8` work. Likewise LiteRT has no FP16.
4. **YOLO26s is bigger than YOLO11s** (10.0M/22.8G vs 9.5M/21.7G, 260 vs 181 layers). Correct any deck
   claim to the contrary; it also means YOLO26s will probably be *slower* on the Pi 5, consistent with
   the arXiv latency findings.
5. **Distillation is solved and cheap** — first-party, feature-based, `distill_model=` one-liner,
   same-family as already planned. Expect only +0.5–1.0 mAP; make sure your variance budget can resolve it.
6. **Pruning is the genuine unknown.** No YOLO26 precedent anywhere. De-risk in week 1 with a throwaway
   DepGraph trace on a fused `end2end=False` YOLO26s. If the fork trips DepGraph, the fuse-first trick
   is the fallback and it makes YOLO26 pruning identical to YOLO11 pruning.
7. **LD / DFL-distribution distillation is off the table for YOLO26** (`reg_max=1`). If ticket 04 was
   considering it, it can only apply to YOLO11 — which makes it a confound, not a shared method.
8. **QAT** is first-party (`quantize=8` in train) but only emits Q/DQ for `onnx`/`engine`; other formats
   *reject* a QAT checkpoint. So QAT is a Jetson/laptop-only option, not a Pi/Android one.
9. **Jetson:** if the board turns out to be JetPack 6 (ticket 10), the TensorRT 10.7+ upgrade is a
   documented prerequisite for any NMS-free INT8 comparison. On an original Jetson Nano (JP4/TRT 8.2)
   it is simply impossible.
